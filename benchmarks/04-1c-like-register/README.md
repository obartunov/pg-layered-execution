# 1C-like analytical register report v1

```bash
benchmarks/04-1c-like-register/load.sh <PGPORT> [PGHOST] [DBNAME]   # default DB: onec
benchmarks/04-1c-like-register/run.sh  <PGPORT> [PGHOST] [DBNAME]
```

Use a database of its own. This dataset reuses the table NAMES of
`reconstructed-v1` (benchmark 02) and must not be loaded over it.

## The hypothesis

> On one and the same annual section of the register, a compact batch pipeline
> lowers the cost of reading, decoding, joining and aggregating relative to the
> stock PostgreSQL executor.

The kernel measured is:

    scan annual register section
      -> join calendar
      -> join account dictionary
      -> group by year, account group, company
      -> debit turnover, credit turnover, net turnover

## What this is not

This is an **analytical report kernel**, not 1C and not a 1C workload. It has
no documents, no posting, no locks, no transactions under contention, no
concurrent users and no write path. Nothing here says anything about how a real
1C installation behaves. The name describes the *shape* of the report — a wide
turnover report over an accounting register — not its provenance.

The distribution is a deterministic synthetic one. No real register was
available to model, so it is not called realistic.

## Mapping onto a 1C-like register

| table | element |
|---|---|
| `reg_buh` | the register's movement records for one closed annual section |
| `dim_period` | the calendar: `period_key -> year, month` |
| `dim_account` | the chart of accounts: `account_key -> account_group` |

`amount_dt` and `amount_kt` are the debit and credit turnovers of a movement;
`debit_key` and `credit_key` are correspondence columns, carried in the row but
not aggregated; `payload` is an unrelated column that keeps the row from being
narrower than the projection the report reads.

## Dataset `1c-like-v1`

Generated by `gen_data.py` (seed 20260923), loaded identically into heap,
pgColumnar and the ZLFS zone. Measured by `verify.sql`, not asserted:

    rows                                1 000 008
    distinct period_key                        12     one closed year
    distinct company_key                       50
    distinct account_key                      200     in 4 groups of 50
    distinct (company, account) pairs       10 000     = 50 x 200
    account_keys per company (min/max)    200/200
    companies per account (min/max)         50/50
    report groups                             200     1 year x 4 groups x 50 companies
    group size (min/max rows)          5000/5001
    amount_dt, amount_kt (min/max)        0/99999

The pair count is the check that matters. `company_key` and `account_key` must
not determine each other, or the join is trivial and the group count collapses.
The first version of the generator advanced both with co-prime strides per row,
which looks independent and is not — the pair then cycles with
`lcm(50,200) = 200`, giving 200 pairs out of 10 000 and exactly one company per
account. `verify.sql` caught it; the generator now takes the two keys from
independent coordinates of the row index.

**Money columns are integers**, and the two sums are accumulated in `int64`.
For this dataset that is exact, which is what lets every path be compared by
one checksum. It is a property of the benchmark, not support for PostgreSQL
`numeric`.

## The paths

All five read the same rows — the whole annual section, periods 1..12 — and
produce the same three aggregates. There is only one year in the dataset, so
nothing here compares a vanilla scan of ten years against a zone holding one.

| storage | execution |
|---|---|
| heap | PostgreSQL row executor |
| pgColumnar | stock `PgColumnarScan` |
| heap | xp_batch pipeline |
| pgColumnar | xp_batch Fold adapter |
| ZLFS annual zone | xp_batch pipeline |

Two stock baselines, never averaged together:

* **`vanilla_single`** — `max_parallel_workers_per_gather=0`, `jit=off`. An
  executor-architecture comparison on one core, matching how the xp_batch paths
  run.
* **`vanilla_default`** — planner left alone. The practical baseline. Its plan
  is `Finalize HashAggregate -> Gather -> Hash Join -> Hash Join -> Partial
  HashAggregate -> Parallel Seq Scan`, with `max_parallel_workers_per_gather=2`.

`jit` is off in both, and not by choice: this server is built without LLVM, so
`jit`'s boot value is `off`. **JIT is therefore not exercised at all here**, and
the practical baseline is "parallel, no JIT" rather than "PostgreSQL defaults".

## Results

PG 20devel `5713b43` + `patches/required/0001-executor-batch-api.patch`,
pgcolumnar `5b20ae8` + `patches/pgcolumnar-alpha5/`, one container, warm runs,
5 per path, median. Milliseconds from another machine are not comparable with
these; the checksum, the group count and the shape of the breakdown are.

| path | median | min | max | source | join1 | join2 | agg |
|---|---|---|---|---|---|---|---|
| heap + PostgreSQL, single-core | 328.9 ms | 309.4 | 344.9 | — | — | — | — |
| heap + PostgreSQL, defaults (2 workers) | 171.8 ms | 164.6 | 174.6 | — | — | — | — |
| pgColumnar + `PgColumnarScan`, single-core | 442.9 ms | 433.7 | 497.6 | — | — | — | — |
| heap + xp_batch | 25.1 ms | 22.7 | 26.6 | 18.0 | 1.9 | 2.1 | 3.1 |
| pgColumnar + xp_batch Fold | 35.6 ms | 35.5 | 35.9 | 28.9 | 1.9 | 1.9 | 2.9 |
| ZLFS zone + xp_batch | 7.0 ms | 6.7 | 7.2 | 0.0 | 1.9 | 2.1 | 3.0 |

All runs, not just the medians, are in `raw/`. There is no phase breakdown for
the SQL paths and none has been invented from their totals.

**`source=0.0 ms` for ZLFS does not mean reading is free.** The zone is already
materialized in memory; the read it would have paid for happened at build time.
That cost is measured separately and kept out of query latency:

    ZLFS zone build           82 ms, 19 531 KB   (5 columns, 1 000 008 rows)
    heap reg_buh                       57 MB
    pgcolumnar reg_buh_col           9 776 kB

For the columnar arm the run also reports `rowgroups=7 copied=0`: the predicate
covers the whole section, so every row group is served by pointing at
pgcolumnar's decoded stream and nothing is materialized. The 28.9 ms of source
time is pgcolumnar's own read and decode, not conversion into the batch layout.

## Does the required core patch change the row path?

`patches/required/0001-executor-batch-api.patch` adds `ExecProcNodeBatch()` and
its fallback; no plan in this benchmark calls it. Measured rather than
asserted, by `stock-vs-patched.sh` — the same SQL, same dataset, two servers
built from the same commit, both on an ordinary plan:

    stock 5713b43      median 347.0 ms   (328.5 – 372.2)
    patched 5713b43    median 345.2 ms   (317.4 – 364.2)

The ranges overlap almost entirely and the medians differ by 0.5%. On this host
the patch does not measurably change the row path, so the patched server's row
path is used as the vanilla baseline.

## Correctness gate

Run before any timing, and timing is not taken if it fails:

* one checksum across all five paths, over all three aggregates and all keys;
* the same group count everywhere;
* `net = debit - credit` for every path and, separately, for every group;
* ZLFS and pgColumnar called twice in the same backend return the same result;
* an empty range (periods 90..91) returns 0 groups, a boundary range (period 12
  alone) returns 100, and the full section afterwards returns 200 again — so no
  state is carried between calls.

Checksum: `6854be25aa9bc0667f8163a679189dbe`, 200 groups, in
`expected-checksum.txt`. Timing is excluded from it.

## What this experiment does and does not support

Supported by the measurement:

* On identical rows and an identical result, the compact batch pipeline
  completes this report faster than the stock executor on the same storage:
  25.1 ms against 328.9 ms on heap, single-core, and 35.6 ms against 442.9 ms
  on pgColumnar. Both are whole-path comparisons.
* Operator cost barely depends on the source: `join1 + join2 + agg` is
  6.8–7.1 ms in all three pipeline paths, so the difference between them is the
  source.
* Carrying a second resource and producing three aggregates instead of one does
  not change that shape.

Not tested here:

* Types beyond `int4` — no `numeric`, no varlena, no NULLs in the measured
  columns.
* MVCC under concurrent writers; every measurement is on a static dataset.
* Concurrency, spill to disk, or memory pressure: the hash tables are fixed-size
  and the run errors rather than spilling.
* Planner integration. These pipelines are hand-wired inside an SRF; the
  planner does not build them, so the advantage does not carry to ordinary SQL.
* JIT, which this build does not have.
* Anything about 1C.
